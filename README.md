# Fortis Secured Web Experience

Fortis Secured delivers a premium marketing site and role-aware client portal built with React, Tailwind CSS and Appwrite. The
public landing page highlights Fortis services, platform capabilities and lead capture, while the secure portal surfaces
incidents, guard tasks, assets and KPI stats aligned to the supplied PRD.

## Tech stack

- **Frontend**: React (Vite) with Tailwind CSS
- **Design language**: Manrope font, glassmorphism gradients inspired by the Fortis colour palette
- **Authentication & data**: Appwrite (email/password, SSO, MFA ready)
- **Deployment targets**: Vercel for the frontend, Appwrite Cloud / self-hosted for backend services

## Getting started

```bash
npm install
npm run dev
```

Visit `http://localhost:5173` for the marketing site. The portal is available at `/portal` and will prompt for credentials
unless an active Appwrite session exists.

### Environment variables

Copy `.env.example` to `.env.local` (or configure in Vercel) and populate the Appwrite identifiers:

```ini
VITE_APPWRITE_ENDPOINT=https://cloud.appwrite.io/v1
VITE_APPWRITE_PROJECT_ID=your-project-id
VITE_APPWRITE_DATABASE_ID=security
VITE_APPWRITE_INCIDENTS_COLLECTION_ID=incidents
VITE_APPWRITE_ASSETS_COLLECTION_ID=assets
VITE_APPWRITE_SHIFTS_COLLECTION_ID=shifts
VITE_FINANCE_INTEGRATION_ENABLED=false
```

In production, missing required `VITE_APPWRITE_*` values now trigger a fatal config screen. Demo/sample-data behavior should only be used in development with `VITE_ENABLE_DEMO_MODE=true`.

### Appwrite configuration

1. Enable email/password auth, desired OAuth providers (SSO) and multi-factor authentication in Appwrite.
2. Export server-side Appwrite credentials for schema automation:

```bash
export APPWRITE_ENDPOINT="https://fra.cloud.appwrite.io/v1"
export APPWRITE_PROJECT_ID="68fbe225003cf4576a12"
export APPWRITE_DATABASE_ID="<your-database-id>"
export APPWRITE_API_KEY="<server-api-key-with-databases-scope>"
```

3. Provision the core portal schema (idempotent, safe to re-run):

```bash
npm run schema:provision
```

Expected output includes a summary table for `collections`, `attributes`, and `indexes` with `created/skipped/failed`.

4. Verify schema completeness (CI-safe; exits non-zero if anything is missing):

```bash
npm run schema:verify
```

5. Run tenancy and gold-path smoke checks:

```bash
npm run smoke:tenancy
npm run smoke:gold-paths
```

6. Run compliance automation scan (dry run or live):

```bash
npm run compliance:scan -- --dry-run
# live write mode:
npm run compliance:scan
```

7. Run operations/intelligence engines:

```bash
node scripts/margin-monitor.mjs --dry-run
node scripts/forecast-run.mjs --dry-run
node scripts/profit-snapshot.mjs
node scripts/sla-calc.mjs
node scripts/contract-health-run.mjs --dry-run
node scripts/migrate-entityId.mjs --dry-run
node scripts/acquisition-simulate.mjs --dry-run
node scripts/strategic-forecast-run.mjs --dry-run
node scripts/risk-evaluate.mjs --dry-run
node scripts/cashflow-run.mjs --dry-run
node scripts/concentration-scan.mjs --dry-run
node scripts/margin-leakage-scan.mjs --dry-run
node scripts/contract-dependency-scan.mjs --dry-run
node scripts/resilience-run.mjs --dry-run
node scripts/employment-risk-scan.mjs --dry-run
```

8. Run integrity and production gate checks before deploy:

```bash
npm run data:check
npm run verify:production
```

9. Deploy the frontend to Vercel, adding the Appwrite environment variables. The site is a static export generated by `npm run build`.

### Email-only notifications (outbox + serverless sender)

Notifications are email-only and queued in `notification_outbox`. Client code only enqueues outbox records; email is sent server-side by `POST /api/notify`.

Required server env vars:

```ini
APPWRITE_ENDPOINT=https://fra.cloud.appwrite.io/v1
APPWRITE_PROJECT_ID=...
APPWRITE_DATABASE_ID=...
APPWRITE_API_KEY=...
APPWRITE_NOTIFICATION_OUTBOX_COLLECTION_ID=notification_outbox
NOTIFY_SECRET=...
SMTP_HOST=...
SMTP_PORT=587
SMTP_USER=...
SMTP_PASS=...
EMAIL_FROM=...
APP_URL=https://your-portal.example
OPS_EMAIL=ops@your-company.example
```

Retry pending/failed outbox items:

```bash
npm run notifications:retry
```

### Schema troubleshooting

- `Missing required environment variables`: set `APPWRITE_ENDPOINT`, `APPWRITE_PROJECT_ID`, `APPWRITE_DATABASE_ID`, `APPWRITE_API_KEY`.
- `Type mismatch` during verify: existing collection schema differs from the source of truth in `scripts/schema/collections.js`.
- `Index ... failed`: existing data can block `unique` index creation. Clean or deduplicate records, then re-run `npm run schema:provision`.
- `fetch failed`: network/sandbox restriction; run the command in an environment with outbound access to Appwrite.
- `smoke:tenancy` failure: review `src/lib/tenancyScope.js` and route/service permission mapping to ensure Model A scoping is still consistent.
- `smoke:gold-paths` failure: verify required collections/attributes/indexes for timesheets/exports/compliance/incident workflow exist in Appwrite and check the smoke script output for the failed check id.
- `compliance:scan` failure: verify `compliance_rules`, `compliance_flags`, `staff_profiles`, and `notification_outbox` collections and email template event types are provisioned.
- `notifications:retry` failure: confirm `NOTIFY_SECRET`, `APP_URL`/`NOTIFY_URL`, SMTP credentials, and `notification_outbox` schema.

### Deployment notes

- **Vercel** – Use the default Vite static site preset (`npm run build`, output folder `dist`). No additional rewrites are required.
- **GitHub Pages** – Ensure the site is published from the `dist/` folder and that the branch is configured for Pages. The Vite configuration now sets `base: './'`, and the router consumes `import.meta.env.BASE_URL` so asset URLs resolve correctly even when the site is hosted from a sub-path such as `/Fortis-Secured/`.

- `npm run migrate:entity` – Backfill/normalize `entityId` onto existing financial + contract records
- `npm run acquisition:simulate` – Append acquisition simulation snapshots (never mutates live financials)

### Timesheet Runbook (Reject -> Edit -> Resubmit -> Approve)

1. Staff: open `/portal/time`, open current week, add/clock entries, then submit.
2. Manager/Admin: open `/portal/time-approvals`, reject with reason.
3. Staff: open the rejected timesheet and edit any entry.
   - Service behavior: timesheet auto-reopens to `open`, rejection fields are cleared, entries reset to `open`.
4. Staff: submit again (status becomes `submitted`).
5. Manager/Admin: approve in approvals queue.
   - Service behavior: entries become `approved`, timesheet transitions to locked state.
6. Admin: run `/portal/payroll` exports for approved/locked source data.

### Phase 8 Runbook (Entity Isolation + Alerts + Board)

1. Provision and verify schema:
   - `npm run schema:provision`
   - `npm run schema:verify`
2. Backfill entity ownership:
   - `node scripts/migrate-entityId.mjs`
3. Validate entity isolation:
   - Run `node scripts/data-integrity-check.mjs` and confirm there are no `*_ENTITY_MISMATCH` or `*_MISSING_ENTITY` critical findings.
   - As a non-global admin user with scoped entity access, open `/portal/reports` and verify other-entity records are absent.
4. Trigger alert engines (non-dry run in staging):
   - Margin anomaly: `node scripts/margin-monitor.mjs`
   - Concentration risk: `node scripts/concentration-scan.mjs`
   - Margin leakage: `node scripts/margin-leakage-scan.mjs`
   - Contract dependency risk: `node scripts/contract-dependency-scan.mjs`
   - Resilience risk: `node scripts/resilience-run.mjs`
   - Employment risk awareness: `node scripts/employment-risk-scan.mjs`
5. Trigger strategic/snapshot engines:
   - `node scripts/acquisition-simulate.mjs`
   - `node scripts/strategic-forecast-run.mjs`
   - `node scripts/risk-evaluate.mjs`
   - `node scripts/cashflow-run.mjs`
6. Verify board dashboards:
   - `/portal/reports` for board/investor metrics
   - `/portal/risk-alerts` for unified alerts
   - `/portal/cashflow`, `/portal/resilience`, `/portal/employment-risk`, `/portal/tender-workbench`, `/portal/entities`
